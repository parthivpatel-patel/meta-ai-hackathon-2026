# Performance methodology

Use the measured evidence in `TEST_EVIDENCE.md` and its JSON artifacts. Record the tested commit/image, headless Chromium environment, loopback public container limits and whether WebGL is software-rendered or disabled. Local warm timings do not establish public Render cold-start performance or physical mobile throughput.

The procedural model has no downloaded mesh assets. Three.js is pinned and loaded through the lazy workstation chunk; the established investigation library remains a separate view. The graphics chunk may exceed Vite's500KiB advisory threshold; retain actual raw/gzip sizes rather than suppressing the warning. Camera renders are demand-driven. Pixel ratio is capped at1.5; geometry/materials/listeners/context are disposed on unmount. No animation-driven physics or continuous renderer loop is used.

Browser sampling is fixed at2Hz with bounded stepping; simulation periods1/2/5seconds are explicit recipe parameters. Data is precomputed on demand, not streamed from hardware. Charts show at most120 samples per associated sensor. Import/history/event counts are bounded. Performance tests should distinguish application generation time, UI/network/download latency, render cadence under camera interaction, JS heap snapshots and true retained-memory leakage. GC-assisted measurements are diagnostic samples, not a no-leak guarantee.

The managed workspace repeatedly ran out of disk while accumulating local Docker layers. Only disposable builder cache/unused images and prior local test containers were removed; source and required evidence were preserved. The production build was retried after recovery. This is an execution-environment limitation, not a repaired production storage guarantee.
